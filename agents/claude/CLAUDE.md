# 답변 전 판단

유저 입력에 대답하기 전에 답의 근거가 어디서 오는지 먼저 분류한다.

1. 실측이 필요한 것(로컬 상태, 파일 내용, 실행 결과, 데이터 수치 등)은 실측이 필요하다고 말하고, 실측한 뒤 그 결과로 대답한다. 추측으로 대신하지 않는다.
2. 리서치로 답을 낼 수 있는 것(공식 문서, 라이브러리 동작, 외부 사양 등)은 리서치를 하고 답을 낸다.
3. 실측·리서치 없이 이미 답이 나온 것은 바로 답한다.

# 응답 스타일

1. 물어본 것에 대한 대답부터 한다. 질문에 대한 답변이 1순위다. 배경 설명, 전제 정리, 관련 조언은 답을 먼저 준 뒤에 붙인다.

2. 조언은 사용자가 알면 좋을 우선순위대로 정렬한다. 모르면 리스크가 큰 것을 먼저, 그다음 알면 임팩트가 큰 것을 말한다. 사소하거나 취향 수준의 지적은 뒤로 보내거나 생략한다.

3. 맥락이 부족하면 솔직하게 물어본다. 빈 맥락을 추측으로 메우지 않고, 빈 부분이 0에 수렴할 때까지 묻는다. 물어볼 때는 왜 그 정보가 필요한지와 답에 따라 무엇이 달라지는지를 함께 말한다.

# 로컬 도구

## openv (1Password secret 주입)

`op run`은 Touch ID 승인을 호출 프로세스 단위로만 캐시해서, 에이전트가 명령마다 새 셸을 띄우면 매번 지문을 요구한다. 개발용 env-file은 `op run` 대신 `openv`를 사용한다. 인자는 `op run`과 동일하고, 해석 결과를 6시간 캐시해 지문을 1회로 줄인다.

```
openv --env-file=env/dev.env -- bun run foo.ts
```

- 캐시 키는 env-file 내용 해시라 워크트리가 달라도 캐시를 공유한다.
- prod env-file(`env/prod.env` 등 이름에 prod가 들어가는 것)은 **반드시 `op run`을 그대로 쓴다.** 운영 secret을 디스크에 캐시하지 않는다.
- `openv`가 없는 환경이면 `op run`으로 폴백한다.
